# ADR 0002: архитектура вертикального среза

- **Статус:** принято
- **Дата:** 2026-07-28
- **Уточнено:** 2026-07-28 — battlefield отделён от viewport после
  продуктового решения о большой прокручиваемой карте.

## Контекст

Первый исполняемый срез должен одновременно проверить разрушаемый рельеф,
несколько разных способов доставки оружия, яркую presentation и удобные
touch-controls. При этом механика обязана оставаться детерминированной и
тестироваться без браузера.

В [архитектурном предложении](../architecture.md) Phaser рассматривался как
кандидат, но для текущего объёма не требуются scene graph, asset pipeline или
framework physics. Дополнительный runtime усложнил бы первый deploy и не
заменил бы собственную модель изменяемого материала.

## Решение

1. Реализовать доменное ядро как независимые TypeScript-модули в `lib/game/`.
2. Хранить рельеф battlefield в дискретной сетке `2880 × 720` на
   `Uint8Array`, отдельно от фиксированного Canvas viewport `960 × 540`.
3. Считать баллистику фиксированными шагами с явно переданными параметрами и
   seeded randomness.
4. Рисовать поле и эффекты через один Canvas 2D; camera adapter переводит
   world-space в фиксированный viewport и поддерживает pan, zoom, minimap и
   auto-follow.
5. Использовать React только для жизненного цикла, доступного HUD, магазина и
   элементов ввода.
6. Передавать результат симуляции в presentation; частицы, звук и shake не
   могут менять урон или материал.
7. Собирать приложение через vinext/Vite, сохраняя совместимость с ChatGPT
   Sites и обычным локальным браузером.

## Последствия

Положительные:

- ядро быстро запускается в Node и покрывается unit-тестами;
- отсутствует обязательный внешний asset/runtime слой;
- Canvas даёт прямой контроль над terrain bitmap и бюджетом частиц;
- terrain bitmap обновляется по dirty bounds механической операции; полный
  проход по сетке требуется только для нового battlefield или безопасного
  fallback;
- touch/keyboard accessibility остаётся в семантическом DOM.

Ограничения:

- renderer, camera и object pooling поддерживаются проектом самостоятельно;
- большая material grid повышает требования к памяти и не отменяет
  профилирование на физическом телефоне;
- Canvas 2D может стать узким местом для значительно большего каталога или
  тяжёлого post-processing;
- нет готовых сцен, tween timeline и inspector из игрового framework.

Если профилирование на целевом Android-устройстве покажет системный предел,
переход на WebGL/Phaser/Pixi оформляется отдельным ADR. До такого измерения
второй renderer не добавляется.
